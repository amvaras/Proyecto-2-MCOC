## Observaciones que debe conocer el grupo

1. **Falta la evidencia real de HPC.** `E14_HPC_PENDIENTE.md` lo reconoce correctamente. No se debe inventar un ID ni presentar variables `SLURM_*` como prueba de ejecución remota.
2. **La prueba mínima incluida no demuestra paralelismo:** `configs/e14/hpc_smoke.json` usa N=1, una tarea y un input reutilizado. Es útil para comprobar acceso, entorno y recolección. Después hace falta un batch nuevo con varios chunks, concurrencia mayor que uno y outputs del cluster. Si todos los inputs se reutilizan, declararlo; para demostrar ejecución térmica allí, incluir también algún input nuevo con costo presupuestado.
3. Monte Carlo remuestrea un **modelo discreto de 24 escenarios**. N=10000 por plan no significa 10000 ensayos independientes de hormigón ni 10000 solves. Una curva y una historia climática permanecen completas dentro de cada realización; todos los planes comparten el banco para una comparación emparejada.
4. La independencia es condicional al generador y al modelo de muestreo. Las semillas derivadas con `SeedSequence` permiten separar realizaciones sin depender del orden de ejecución; verificar semillas distintas por sí solo no prueba independencia experimental. Véase la [documentación oficial de NumPy](https://numpy.org/doc/stable/reference/random/parallel.html).
5. Los IC son puntuales y condicionales. Para `curado_rapido`, MC=94,49% e IC95%=[94,025%; 94,929%] no contienen la referencia exacta 95%. Es posible con cobertura nominal del 95%; no se cambió la semilla para forzar concordancia. Los límites se comprobaron contra el [procedimiento binomial exacto de NIST](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/exacbino.htm).
6. Ninguno de los ocho planes alcanza Pf≤5%: el mínimo exacto es **85%**, frente a **84,60%** estimado por MC. Esto describe el resultado físico bajo los supuestos; no es un fallo del workflow ni una estimación de riesgo real de obra validada.
7. En el ZIP recibido, el apartado Git de `E14_CIERRE_F02.md` describía otro checkout y un momento anterior. La auditoría partió de `codex/e13`, HEAD `9fc62cd4d5d0a4ee36810827add3ceb9e00f6527`, ya publicado como E13. Ese SHA **no identifica E14**. La publicación posterior autorizada usa la rama `codex/e14` y la etiqueta `entrega-e14`; véase [identificación para Canvas](E14_PUBLICACION.md).

## Cómo completar lo pendiente

1. Confirmar con el grupo o ayudante el centro, acceso autorizado, cuenta, partición y módulos. No se requieren contraseñas por este chat.
2. Instalar y comprobar el entorno Linux del proyecto; conservar Python/NumPy declarados y ejecutar la verificación offline antes de enviar trabajos.
3. Hacer primero la prueba mínima de `E14_HPC_PENDIENTE.md`. Preparar después un destino **nuevo** para un batch con varios chunks, semilla registrada y concurrencia acotada; no sobrescribir resultados oficiales.
4. Enviar con `scripts/hpc/submit.sh`, inspeccionar con `squeue` y `sacct --array`, y recolectar con `scripts/hpc/collect.sh`. Los [arrays de Slurm](https://slurm.schedmd.com/job_array.html) asignan un índice a cada tarea; [sacct](https://slurm.schedmd.com/sacct.html) permite comprobar estados y códigos de salida.
5. Conservar JobID, logs `%A_%a`, manifest, proofs runtime, accounting y resultados agregados. Todos los índices deben finalizar correctamente; un envío aceptado todavía no acredita terminación. El código ya exige estas comprobaciones.
6. Publicar E14 e identificar su SHA. Canvas pide repositorio y commit evaluado; agregar el JobID representativo cuando corresponda al cluster.
